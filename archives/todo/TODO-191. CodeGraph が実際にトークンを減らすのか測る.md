## きっかけ

`.codegraph/` を入れた（TODO-189）が、効果を測っていなかった。

## やったこと

### 出力量だけの比較

`codegraph explore` 1 回の出力量と、同じ答えに至る grep→read の出力量を
バイト数で比べた。

| 問い | codegraph 1 回 | ファイル全体読み | 周辺だけ読み |
|------|---------------|-----------------|-------------|
| フィルタと検索文字列の処理 | 18,938 | 78,078 | 14,224 |
| `SchedDataFile.save()` の影響範囲 | 22,167 | 69,861 | 728（grep のみ） |

**効果は問いの型で逆転する。** どこを読めばいいか分からない問いでは
3〜4 倍有利だが、grep 一発で答えが出る問いでは桁で不利。

### 実際の消費の比較

同じ問い（「ゴミ箱から予定を復元したときの経路」）を `general-purpose`
2 本に投げた。一方は CodeGraph 禁止、他方は Read/Grep 禁止。

| | grep 側 | CodeGraph 側 | 差 |
|---|---|---|---|
| トークン | 77,679 | 77,132 | −0.7% |
| ツール呼び出し | 22 | 15 | −32% |
| 時間 | 104 秒 | 96 秒 | −8% |
| 答え | 正しい | 正しい | 同じ |

**この規模（36 ファイル・17,440 行）ではトークンが減らなかった。**
往復が 32% 減ったのにトークンが 0.7% しか動かなかったのは、
`codegraph explore` の出力が問いの大小によらず 19〜22KB と大きく、
往復削減のぶんを出力量が相殺したため。前半の測定から予測できた結果と
一致する。

答えはどちらも正しかった。`add_sde` は `SchedDataFile`（`ytsched.py:781`）と
`SchedData`（同 1051）の 2 つあるが、両方とも正しく後者を特定した。

### 日本語クエリが空振りする原因

CodeGraph 側の担当は、日本語のクエリで 3 回続けて空振りした
（「ゴミ箱から予定を復元する経路」「ゴミ箱 復元」「削除した予定を元に戻す
処理」）。4 回目の英語 `restore from trash handler` でヒットした。

原因を切り分けたところ、**日本語はクエリとして完全に無視されていた**。

| クエリ | 結果 |
|---|---|
| `trash` | Found 36 symbols |
| `trash 復元` | Found 36 symbols |
| `trash 全然関係ない日本語` | Found 36 symbols |

日本語だけのクエリは検索語がゼロになるため空振りする（`予定`・`ゴミ箱`
単体もすべて `No relevant code found`）。`codegraph query` も同じ。

回避策は 3 つ確かめた。

- **ファイル名で引く。** `codegraph explore "trash_handler.py"` が効く
- **英語の識別子を混ぜる。** 日本語は残しても害は無い（無視されるだけ）
- **名前が分からなければ `codegraph query "<英語>" -l 5` で先に引く**

### 文書に残した

- `~/.claude/CLAUDE.md` に「### クエリは英語で書く」を足した。
  日本語が無視されるのは CodeGraph の仕様でプロジェクトを選ばないため。
  **`<!-- CODEGRAPH_START -->` 〜 `<!-- CODEGRAPH_END -->` の外側に置いた**
  （内側は CodeGraph が管理する範囲で、更新で消える）
- このリポジトリの `CLAUDE.md` には「## CodeGraph」を足し、測った結果と
  ytsched 固有の使いどころだけを書いた

グローバル側の変更は本来 admin の項目にすべきだが、利用者の判断で
この項目にまとめた。

## テスト

`verifier` に、書いたとおりのコマンドを叩かせて主張を確かめさせた。

- `codegraph explore "trash_handler.py"` がファイル名だけで引けるか
- `codegraph query "restore" -l 5` がシンボル名と行番号を出すか
- `trash` と `trash 全然関係ない日本語` の結果が一致するか

- 追記が CodeGraph のマーカーの外にあるか
- 書式が周囲と揃っているか

すべて主張どおりで、食い違いは無かった。

## 分担の振り返り

**各担当が何を見つけたか。** `general-purpose` 2 本は測定対象なので、
見つけたものより「同じ問いに同じ正解を出したこと」に意味があった。
両方とも `add_sde` の 2 つある定義を正しく区別し、`_restore()` が
ゴミ箱側のエントリを消さない点も揃って報告した。答えが割れていたら
消費の比較そのものが成立しなかったので、これは前提条件が満たされた
という結果。`verifier` は食い違いを 1 件も見つけなかった。ただし
main が測定済みの数値を書いただけなので、見つからないのが自然。

**見込みと食い違ったのはなぜか。** 見込みには `verifier` を書いて
いなかった。文書だけの項目なので不要と考えたが、コマンド例を 3 つ書いた
時点で「書いたとおりに試せるもの」に該当し、規約どおり分ける必要が
出た。**測定結果を文書化する項目は、数値とコマンドが必ず記述に入るので、
最初から確認の担当を見込みに入れておくべきだった。**

もう 1 つ、料金が見込みより膨らんだ。main が 76%（$3.0）を占めている。
原因は測定の前半を main が全部やったこと（バイト数の比較、日本語の
原因切り分け）。この部分は Bash を 10 回以上叩いており、そのたびに
会話全体を読み直している。

**次に同じ規模の項目をやるなら。** 測定の前半（バイト数の比較と、
日本語が無視されることの切り分け）は、手順が決まっていて判断が要らない
ので `runner`（Haiku / effort low）に投げられた。実際にやったのは
「コマンドを叩いて数字を並べる」だけで、判断は数字が出揃ってからの
1 回で足りる。main が 76% を占めたのは、この定型作業を自分で抱えたため。
**測定そのものは runner、解釈と文書化だけ main、確認は verifier** の
3 者に分ければ、同じ結論を半分以下の料金で出せたはず。
