# TODO-018. データ形式の見直し（何を変えるかを決める）

見込み: main = Opus 5 / effort high、担当 = main のみ
実施: main = Opus 5 / effort high、担当 = main + verifier

## きっかけ

`CLAUDE.md` と `TODO.md` に「データ形式（タブ区切りテキスト）とデータ
ディレクトリは、既存データとの互換のため変えない」と書いてあった。この
前提を見直したいという話から立てた。

立てる前に 2 点を確認し、次の答えを得ている。

- 見直す範囲は決まっていない。調べたうえで選択肢を出してほしい
- 既存データとの互換は、**移行ツールを作って一度で変換してよい**

さらに、「重要」「取り消し」「ToDo」の判定については、**使い方の柔軟性を
重視して今のまま変えない**という条件が付いた。

この項目では**何をどう変えるかを決めるところまで**をやり、実装と移行
ツールは別の項目にした。

## やったこと

### 調べたこと（すべて実測）

旧形式の問題を、実際にコードを動かして確かめた。

- **往復（保存 → 読み込み）で内容が一致しない。** 本文のタブが空白に
  潰れる。表題にタブが入ると**列がずれて場所に化ける**。全角括弧が
  半角になる。`&nbsp;` が空白になる。本文に書いた `<br />` が改行に
  なる。末尾の改行が変わる
- **1 行の不備でその日のファイル全体が読めない。** 末尾に空行が 1 つ
  あるだけで `ValueError` が上へ抜ける。日付が `2026/13/45` でも同じ
- **utf-8 でも euc_jp でも読めないバイトが混じると 0 件扱いになり、
  操作を 2 回すると元のデータが消える。** 1 回目の保存で元が `.bak` へ
  退避され本体は新しい 1 件だけになり、次の保存でその本体が `.bak` を
  上書きする
- **「重要」「取り消し」の判定が、入力直後と再読み込み後で食い違う。**
  `（重要）打合せ` は入力直後 `is_important()` が False、保存して
  読み直すと True。全角括弧の半角化を「読み込み時」にやっているため。
  **判定方法は変えない条件だが、現状はそもそも正しく効いていなかった**
- 検索は最大 1825 ファイル（`SEARCH_MODE_MAX_DAYS = 365 * 5`）を
  1 日ずつ開く

### 決めたこと

選択肢と得失を出して利用者に選んでもらった。

| | 決定 |
| --- | --- |
| 保存形式 | JSON Lines（1 行 1 件の JSON） |
| ファイルの置き方 | 1 日 1 ファイルのまま（`YYYY/MM/DD.jsonl`、ToDo は `ToDo.jsonl`） |
| 文字コード | utf-8 のみ |
| 壊れた行 | その行だけ飛ばし、ファイル全体は捨てない |
| 読み込み時の文字置換 | やめる。判定・検索の照合時にだけ揃える |

正規化に `unicodedata.normalize("NFKC", …)` を使う案は**検討して
やめた**。`㍿` → `株式会社`、`①` → `1` まで変えてしまい、旧形式が
置換していた範囲（全角括弧だけ）より広くなる。検索で `㍿` と打っても
当たらなくなるなど、予想しにくい影響が出る。**全角括弧を半角にして
小文字化するだけ**に絞った。

選ばなかった案（タブ区切りのままエスケープ規則を足す／日ごとの JSON
配列／SQLite／TOML）とその理由は `docs/data-format.md` に書いた。

## テスト

コードは変えていないので、テストの追加は無い。

仕様が成立するかの確認は verifier に分けた（報告は
`archives/agents/TODO-018/verifier-report.md`）。文書だけの項目だが、
「載せた JSON Lines が実際に読めるか」「壊れた行がその行だけ飛ぶか」
「移行手順のとおりに変換できるか」「引用した旧形式の問題が本当に現状の
挙動か」は試せるため、TODO-017 で決めた「試せる手順があるなら分ける」に
当てはまる。

verifier は仕様・引用がすべて実際に成立することを確認したうえで、
3 点を指摘した。いずれも取り込んである。

1. `.bak` が消える「2 回保存」は「保存 → 追加 → 保存」の意味で、
   `save()` を続けて 2 回呼ぶだけでは起きない（1 回目で本体が空になり、
   空のファイルは退避しないため）→ 文書に補足した
2. 移行手順 2 が、旧コードの「7 項目に満たない行は空文字で埋める」
   救済に触れていない → 項目数が合わない行の扱いを手順に足した。
   8 個以上ある行は、旧コードが捨てていた 8 個目から先を `detail` の
   続きとしてつなぎ直すことにして、取りこぼさないようにした
3. 移行手順 5 で `htmlstr2text()` を流用すると、全角括弧の半角化も
   一緒にやってしまい手順 6 を破る → 流用しないよう明記した

## 決着のあとに分かったこと（実データの調査）

決着させたあと、既存データ（`tmp_test_data/`、`.gitignore` の `tmp*` で

書き足した。

### いちばん大きかったこと: 文字コードの判定を行単位に変えた

utf-8 でも euc_jp でも読めないファイルが 13 件あるが、**そのすべてで
壊れているのは 1 行だけ**で、同じファイルの他の 33 行は euc_jp で読める。
壊れた 13 行自体も 7 列として成立し、日付も読め、読めないのは `detail` と
`place` の 2〜16 文字だけだった。

旧コードはファイル単位でデコードするので、この 1 行のために 13 ファイル
分 46 行を丸ごと落としている。**行ごとにデコードし、どちらでも読めない
行だけ `errors="replace"` で読めば、1 行も失わずに移せる。**

新形式で「壊れた行はその行だけ飛ばす」と決めたことの正しさが、実データで
裏づけられた形になった。

### 実体参照は 2 回解く必要があった

実データに `&amp;#160;`（二重にエスケープされた NBSP）が 2205 個ある。
旧コードも変換表の先頭でこの形を直していた。`html.unescape()` は
**2 回**かける（3 回以上はかけない。`&amp;amp;` は実データに 0 件）。

決め方の基準は「旧形式で画面に見えていた文字列」にした。`base.html` が
`{% autoescape None %}` なので、ファイルに残った `&quot;` などはブラウザ
側で 1 回デコードされていた。新形式は素のテキストをそのまま出すので、
その 1 回分を移行時に済ませる必要がある。

実データ全体で照合すると、**53628 項目のうち 53460 項目が旧の画面表示と
完全に一致**した。違った 168 項目はすべて意図した変更で、想定外のものは
無かった。

### そのほか

- 移行の対象は `{日}.cgi` と `ToDo.cgi` だけ。`{日}-backup.cgi`（3539）と
  `{日}.cgi.bak`（1977）は別系統で、列の数からして違う
- 時刻に `28:00` が 1 件。旧コードと同じく時を 24、分を 60 で割った余りにする
- `sde_id` は UUID ではなく独自の形（13〜18 文字）。移行で振り直さない
- 仕様書が心配していた「列数の過不足」は実データには無く、全行が 7 列だった

### verifier（2 回目）の指摘

書き足した分は数え直せば再現できる主張を含むので、もう一度確認を頼んだ
（`archives/agents/TODO-018/verifier-report-2.md`）。最重要の 53628 /
168 という数字は一致。3 点の食い違いを見つけてもらい、直した。

1. 「読めないのは 2〜9 文字」→ **実測は 2〜16 文字**。集計スクリプトで
   9 を上限にクリップしていた自分のミス
2. `sde_id`「17〜18 文字」→ 71 件（約 0.5%）が範囲外。13〜18 文字に直した
3. 168 件の内訳表（157 / 7 / 4）は**重なりのある分け方**で、157 のうち
   5 件は数値文字参照の戻しも同時に効いている。合計は正しいので、
   重ならない数え方（152 / 7 / 5 / 4）を注記として足した

集計の範囲が曖昧だった点（`ToDo.cgi` を含むのか、`&amp;#160;` の 2205 個は
どのフィールドか）も、あわせて明示した。
