## きっかけ

TODO-164 で入れた「検索画面のホームボタンのダブルタップ」が、**実機の指で
効かなかった**。1 回目のタップから 350 ミリ秒後にシングルタップの読み直しが
始まるので、それより遅い 2 回目は読み直しに飲まれて消える。タッチで実測した
成立範囲はタップ間隔 270 ミリ秒までで、人の指のダブルタップには狭すぎた。
TODO-164 のテストがマウスの速いクリックしか再現しておらず、これを見逃した。

併せて、**そもそも検索画面から戻れていなかった**ことも分かった。検索モードか
どうかはサーバが `conf.json` の `SearchStr` で決めており、ダブルタップの
`doGet` は URL に `date` と `sde_align` しか載せない。保存された検索語が
残ったまま検索結果が返るので、実測しても検索モードのまま（週パネル 1 枚・
週バー無し）で、基準日が今週の月曜へ移るだけだった。

## やったこと

- **ダブルタップの動作を、どの画面でも
  `doPost({date: 今週の月曜, search_str: "", sde_align: "top"})` に統一した**
  （`reloadHome()`）。`search_str` を空で POST すると `SearchStr` が消えて
  週間表示へ戻る（検索結果の日付欄 `date-post` と同じ道）。
  `MainHandler.post()` はリダイレクト先へ `sde_align` を引き継ぐので、
  先頭合わせもそのまま効く。`view` は `conf.json` に保存されない
  （`get_view()`）ので、月間表示からも週間表示へ戻る
  - 週間表示・月間表示はリダイレクト先の URL が今までと同じになるので、
    結果は変わらない（GET 1 回が POST + リダイレクト + GET になる差はある）
- **検索画面の判定を sessionStorage 方式にした**（TODO-123 のフッターの
  ◀▶ と同じ）。キーは `ytsched_search_home_tap`、幅は TODO-123 と揃えて
  1000 ミリ秒。1 回目は遅延なしで即座に読み直し、2 回目は読み直した先の
  ページで、残しておいたタップ時刻と比べて判定する。TODO-164 で入れた
  350 ミリ秒の遅延はやめた
  - **週間表示・月間表示は今までどおり `clickCount`（350 ミリ秒）のまま。**
    こちらは 1 回目が画面内スクロール（`scrollToDate()`）で済み、ページを
    読み直さないので、メモリ上の `clickCount` が消えない。検索画面のような
    取りこぼしは起きない。350 ミリ秒が指に対して狭いという話は残るが、
    それは別の項目
- **成立したときも記録を消さない。** 消すと、トップ画面の読み込みが終わる
  前の 3 回目のタップが「1 回目」に戻り、検索語つきの POST が 2 回目の遷移を
  上書きして検索画面へ引き戻される（reviewer の指摘 5）
- **ホームボタン以外を押したら記録を捨てる**（`homeTapPointerDownHdr()`。
  window の `pointerdown` に capture で登録）。記録は読み直しをまたいで
  残るので、捨てないと「ホーム → 1 週送り → ホーム」が 1 秒に収まったときに
  ダブルタップと判定され、**1 回押しただけで検索が消える**（reviewer の
  指摘 4）。TODO-123 が `pageTurnPointerDownHdr()` でしている後始末と揃えた
- `docs/User.md` の 1 章と 9.5「検索をやめる」に、ホームボタンのダブル
  タップの説明を入れた。9.5 は「ホームでは検索は解除されない」と書いてあり、
  そのままだと誤りになる（reviewer の指摘 1）

## 決めたこと・やらなかったこと

- **検索画面のダブルタップで履歴が 1 つ増えるのは許容する。** 1 回目も必ず
  遷移するので、`検索@today` → `検索@今週の月曜` → `トップ@今週の月曜` と
  3 つ積まれ、トップから「戻る」を押すと途中の検索画面に戻る。
  sessionStorage 方式（ページの読み直しをまたいで判定する）を選んだ以上
  避けられず、TODO-123 も同じ形。週間表示・月間表示は今までどおり 1 つ
- **週間表示・月間表示の 350 ミリ秒は据え置いた。** 上記のとおり取りこぼしは
  起きないため。ただし「350 ミリ秒は指には狭い」という体感は同じはずなので、
  同じ形の報告が来たらここを見直す

## テスト

`tests/test_browser.py` のホームボタン関連を 9 件に整理した。

- `_in_search_mode()` を足した。TODO-164 で入れた `#footer_date` を見る
  assert は、**あの欄が TODO-119 で削除済みでどちらのモードでも 0 件**に
  なる、意味の無いものだった。`#main` の `data-search-date-to` を見る形に
  直し、`_assert_search_screen()` / `_assert_top_screen()`（週パネル数・
  週バー・検索欄・`data-view`）に分けた。`_open_search` に残っていた同じ
  行も直した
- シングルタップのテストに `_mark()` / `_marked()` を入れた。
  `_open_search` の URL はすでに `date=<today>` なので、**今日が月曜だと
  タップが何も起こさなくても通っていた**（reviewer の指摘 2）
- タッチのテストを 2 件足した。`page.touchscreen.tap()` は CDP でタッチを
  流し込むので、ブラウザが `mousedown` も作る（`homeButtonHdr()` は
  `mousedown` から呼ばれるので、JS で組み立てた `TouchEvent` では届かない）
- 間隔は **500 / 600 ミリ秒**にした。TODO では 300〜600 としていたが、
  検索画面の読み直しにかかる時間を実測すると 180〜360 ミリ秒で、
  300 ミリ秒は境界と重なって 2 回目を狙って置けない（実際、6 回中 3 回
  落ちた）。読み直しより短い間隔は「間を置かずに 2 回押す」テストが
  代わりに見ている（2 回目が遷移の途中に落ちる経路）
- 読み直しが間に合わないときは **skip せずに落とす。** skip にすると、
  「読み直しが遅くて 2 回目が窓に入らない」という、この項目が直そうとして
  いる失敗そのものを緑にしてしまう（reviewer の指摘 3）
- 修正前のコードに対して走らせ、検索画面まわりの 4 件
  （`..._returns_to_the_top_screen_from_search`、タッチの 500 / 600、
  `..._keeps_the_tap_record`）が落ちることを確かめた。指摘 4 の対策を
  外すと `..._tap_after_another_operation_is_not_a_double_tap` が落ちる
  ことも確かめた
- `uv run pytest`・`uv run ruff check`・`uv run ruff format --check`・
  `uv run basedpyright`: すべて通過
- verifier が `--datadir` に一時ディレクトリを指定してアプリを起動し、
  トップページが 200 で返ることを確認。ホームボタンのテストを繰り返し
  走らせて、ぶれないことも確認
