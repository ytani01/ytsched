## きっかけ

予定を編集して保存すると、古い内容はゴミ箱へ入り、新しい内容の予定が
作られる。どちらも同じ `sde_id` だったので、ゴミ箱の行がどの版なのかが
分からなかった。

## やったこと

`sde_id` を `{UUID}-{版}` の形にした。版は 1 から始まる整数で、
**ゼロ埋めしない**（`-1`, `-2`, … `-10`）。

- `SchedDataEnt` に `split_id()` / `id_uuid()` / `id_version()` /
  `format_id()` / `next_id()` を足した。`new_id()` は `{UUID}-1` を返す
- 編集（`fix`/`update`）では、ゴミ箱へ入る側は元の ID のまま、
  新しく作る側の版を増やす。複製（TODO-127）は新しい UUID の `-1`
- ゴミ箱からの復活は、元の UUID を引き継いで版を増やす
  （それまでは新しい UUID を発行していた。TODO-086）
- ゴミ箱画面のグループ化と `?sde_id=` の絞り込みを UUID 部分で行い、
  各行に版を出す
- `fix-id` を新しい形式に合わせ、`trash.jsonl` も対象に加えた
- 走査するファイルの列挙を `SchedDataFile.list_all_files()` に一本化した

旧形式だった予定は、ゴミ箱の行と現在の予定が繋がらない。既に UUID が
一致していた行も、そろって `-1` になって版では区別できない。**ここは
割り切ると決めた**（実データでは 3 行が該当した）。

### 途中で変えたこと

- **版のゼロ埋めをやめた。** はじめは `-001` の 3 桁ゼロ埋めにしていたが、
  999 を超えたら桁が伸びる以上、揃えても揃わないので意味がない
- **複製でも版を増やす案は採らなかった。** 「修正 = 複製 + 削除」に
  揃えられるという話が出たが、複製した直後は元と複製が両方生きている
  ので、そのあと元を修正すると複製と同じ版になって ID が衝突する。
  避けるには修正のたびに全走査が要る。ゴミ箱のグループの意味も
  「同じ予定の編集履歴」から「複製の系統」に変わってしまう

### reviewer の指摘

**復活の版の決め方に穴があった。** はじめは「ゴミ箱」と「復活させる行
自身の日付のファイル」の 2 か所だけを見ていた。日付を変える編集をすると
生きている予定は別の日付のファイルへ移るので、どちらにも現れず、
復活した予定が生きている予定と同じ `sde_id` になる。再現手順つきで
出てきた。テストが通ることを見ても出てこない種類の指摘で、実装した
implementer も、画面を触った verifier も気づいていなかった。

塞ぎ方は **「復活のときだけデータディレクトリ全体を走査して、同じ UUID
の最大の版 + 1 にする」**。「生きている予定の版はゴミ箱の最大 + 1」と
いう見立ては、日付を変える編集でも、復活を 2 回続けても崩れるので、
部分的に見て回るやり方では塞がらない。復活は滅多に使わない操作なので、
全走査の費用を払うことにした。
