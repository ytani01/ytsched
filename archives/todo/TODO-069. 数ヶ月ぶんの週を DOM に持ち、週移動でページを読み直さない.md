## きっかけ

2026-08-26 に、利用者から挙がった。**「週間データをまとめて読み、週移動
したときに毎回読み込むのを避ける」。**

立てるときに「毎回読み込む」がどこを指すのかを実データ（79MB・6736
ファイル）で測った。

| | 応答 | HTML |
|---|---|---|
| 初めて見る週 | 10〜40ms | 230〜270KB |
| 2 回目以降 | 5〜10ms | 同上 |

`SchedData` は既にプロセス内に LRU キャッシュ（20000 件）を持っていて、
**一度読んだ週はファイルを読み直していなかった。** 重いのはファイル
読み込みではなく、毎回 HTML を取り直して描き直しているところ。

そこで利用者に聞いたところ、**「ブラウザが DOM を数ヶ月分読んで
レンダリングの手間も省きたい」**という答えだったので、サーバ側の
先読みではなくブラウザ側で持つ形にした。設定の置き場所も、当初案の
新設 `conf.toml` ではなく既存の `conf.json` に決めた。

## やったこと

### サーバ: 週の数を可変にした

`main_handler.py` の `get()` が `load_sched()` を 3 回呼んで前週・今週・
次週を詰めていたのを、前後 `LoadMonths` ヶ月ぶんへ広げた。

- `weeks` の各要素は `offset`（真ん中の週からの週数）と `monday`
  （その週の月曜）を持つ。検索モードは週の区切りに合わないので
  1 要素で、`monday` は `None`
- `months2weeks()` が月数を週数に直す。1 ヶ月を 30 日として数える
  （暦の月に合わせると、前後で週の数が変わって左右非対称になる）
- 既定は 1 ヶ月＝前後 4 週、計 9 週

### 設定は `conf.json` の `LoadMonths`

**キー名は `LoadMonths`。** 立てたときは `load_months` と書いていたが、
既存のキー（`ToDo_Days` / `FilterStr` / `SearchStr` / `SearchN`）に
合わせた。

- 範囲は 0〜6。数字にならない値も範囲の外も、警告を 1 行出して既定へ
  落とす（TODO-027 と同じ考え方）
- **他の設定と違い、リクエストの引数では変えられない**（`get_conf_arg()`
  を通さず `get_load_months()` が読むだけ）。画面から変える UI も無い。
  `set_conf()` しないので、**手で書いた値は消えない**

### ブラウザ: 見せる週を DOM の中で差し替える

`my.js` に `activeWeekOffset` と、それを動かす関数を足した。

- `weekPanelOf(offset)` / `weekOffsetOfDate(date)` — 週の panel を探す
- `layoutWeeks()` — `my-week-cur` を付け替え、他の週の `left` を
  「いま見ている週から何週ぶん左右か」に振り直す。隣の 2 週にだけ
  `my-week-near` を付ける（指の追従中に見せるのはこの 2 週だけ。
  前後数ヶ月ぶんを全部 visible にすると、送るたびに全部を描くことになる）
- `setActiveWeek(offset)` — 並べ直したうえで、`#cur_day` / `#date` /
  `#date_from` / ヘッダのゲージ / URL を、その週の月曜に揃える
- `moveToMonday()` — 隣の週まで滑らせたあと、送り先が DOM にあれば
  `setActiveWeek()`、無ければ今までどおり `doGet()`

CSS は `.my-week-prev` / `.my-week-next` の 2 クラスをやめ、
`.my-week-panel` を既定で `position: absolute`、`.my-week-cur` だけ
`position: static` にした。**通常フローに残す週を差し替えるのは、
body の高さをその週に合わせるため**（`position: absolute` の週は
高さを決めない）。

**離れた週は `display: none`。** 位置を持たせるのは、いま見ている週と
その隣の 2 週だけ。`position: absolute` の週も、縦にはみ出した分だけ
文書のスクロールを伸ばす（`overflow-x: clip` が切るのは横だけ）ので、
9 週を全部置くと**いちばん背の高い週の分だけ下に空白ができて
スクロールできてしまった**（`scrollHeight` が 1070px から 1351px に
伸びていた）。`display: none` にすると 1070px に戻り、TODO-057 の
ころと同じになる。最初の読み込みで 6 週分のレイアウトを省ける利点も
あった（下の表）。

### `id="date-..."` を全部の週に付けた

TODO-057 で隣の週を出したときは、`id` を今の週にだけ付けて `data-date`
と使い分けていた。`scrollToId()` が隠れている週へ寄せてしまわないため
だったが、週を移るのが DOM の中だけになったので、**寄せる前に週を移す
のは呼び出し側の役目**（`scrollToDate()` / `popstateHdr()`）に変えた。
日付は週をまたいで重複しないので、`id` は全部に付いていてよい。

### ホームボタンのダブルタップ

DOM に持っているデータは古くなる。**ダブルタップが、手で取り直す道。**
もともと `doGet()` していた（TODO-049）ので、動きは変えずにコメントで
その役目を書いた。1 回のタップは今日の週へ移るだけ。

## reviewer の指摘で直したこと

**検索モードの「戻る」が、毎回読み直しになっていた。**
`popstateHdr()` を「`weekOffsetOfDate()` が週を返せば移動、返さなければ
読み直し」と書いたが、検索モードの週は区切りが合わないので
`data-monday` を持たず、**いつも null が返る**。「週が分からない」を
「持っている範囲の外」と取り違えていた。

`scrollToDate()` と同じ形（週が分かれば先に移り、そのうえで
`scrollToId()` を試してから決める）に直した。
`tests/test_browser.py` に 1 件足し、**直す前のコードに戻すと落ちる**
ことも確かめた。

reviewer の残り 2 件（指を追従させている最中に `popstate` が来たときの
一瞬のちらつき／足したログ 1 行）は、そのままにした。前者は「戻るを
押しながら画面に指も触れている」状況で、実機で確かめないと実害が
あるか分からない。

## 測ったこと

実データ（79MB・6736 ファイル）、既定の `LoadMonths=1`（9 週）。

サーバの応答:

| | 応答 | HTML |
|---|---|---|
| 初めて見る週 | 60ms | 704KB |
| 2 回目以降 | 22ms | 同上 |

ブラウザで、**押してから移った先の週になりきるまで**（変更前後で同じ
測り方。どちらも同じ 200ms のスライドを通る）:

| | 週送り 1 回 | 最初の読み込み |
|---|---|---|
| 変更前 | 775ms | 816ms |
| 変更後 | **458ms** | 1002ms |

**週送りは 6 割ほどになり、最初の読み込みが 2 割ほど重くなった。**
1 回でも週を送れば取り返せる。数字はばらつくので中央値。

離れた週を `display: none` にする前は、最初の読み込みが 1283ms
（+344ms）だった。**置く週を 3 つに絞ったぶん、引き換えも小さくなった。**

**verifier の 1 回目の計測では、変更後のほうが遅いという結果が出た**
（変更前 95〜120ms、変更後 273〜302ms）。変更前と変更後で終わりの
見方が違っていたためで、上のように**同じ測り方**に揃えると逆になる。
verifier 自身も「この数値で優劣を断定できるか自信が無い」と付けて
報告しており、**数字だけを受け取らずに測り直したのが正解だった**。
