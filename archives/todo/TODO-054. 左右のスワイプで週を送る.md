## やったこと

`my.js` の末尾にスワイプの処理を足し、`main.html` で `window` に
登録した。触ったのはこの 2 ファイルだけ。

- `touchStartHdr` — 始点を `swipeStart` に覚える
- `touchMoveHdr` — 指が増えていないかを、動いている間も見る
- `touchEndHdr` — 条件を満たしていれば `moveToMonday()` を呼ぶ
- `touchCancelHdr` — 割り込まれたら見送る

**左へ払うと次の週、右へ払うと前の週。** キーボードの → が次の週
なのと揃えた。

### 受け付ける条件

| 条件 | 値 | 理由 |
|------|------|------|
| 横に動いた距離 | 60px 以上 | 触っただけ・押しただけと分ける |
| 横と縦の比 | 横 ≧ 縦 × 1.5 | 縦スクロールと切り分ける |
| 触れていた時間 | 800ms 以内 | ゆっくり動かしたものは払ったと見なさない |
| 始点の位置 | 画面の左右の端 30px より内側 | iOS Safari の画面端スワイプ対策 |
| 指の本数 | 1 本 | ピンチで週が変わらないように |
| 始点の要素 | `input` / `textarea` / `select` の外 | 検索欄で文字を選べるように |

**縦スクロールとの切り分けは、縦の動きが優勢なら無視するだけ。**
1 週間分が画面に収まらない週では上下にスクロールするので、その動きを
週送りと取り違えないようにする。

**iOS Safari の画面端スワイプ（戻る/進む）は OS に取られる。**
こちらでも拾うと二重に効くので、画面の左右の端 30px から始まった
ものは受け付けない。

**4 つとも `passive` で登録した。** `preventDefault()` を呼ばないので、
スワイプの判定が縦スクロールを止めることはない。

**登録するのは `main.html` だけ。** `keyHdr` / `popstateHdr` と同じで、
編集画面ではスワイプが効かない（入力の途中で画面が変わらないように）。

### ゲージの `transition` で代用できるか → できた

立てたときに「まずはこの項目で、ゲージの `transition` で代用できるかを
見る」と決めてあった。**払った直後に針が前の週の位置から今の週の位置へ
0.3 秒かけて動く**のを実測した（`490px` → `428px`)。TODO-049 で入れた
`sessionStorage` の仕掛けが、そのまま効いている。

どちらへ移ったかは針の動きで分かるので、**画面の中身を指に追従させる
必要があるかどうかは、しばらく使ってから決めればよい**。TODO-057 は
残してある。

## やらないと決めたこと

### ピンチズームを止める

verifier が「ピンチで週は変わらないが、ブラウザ自体がピンチズームする」
と報告した（`visualViewport.scale` が 1 → 3.58）。`touch-action` や
`user-scalable=no` を入れれば止まるが、**入れない**。

**このアプリはピンチでの拡大を意図して許してある。** `base.html` の
viewport に `user-scalable=no` を書いていないのはそのためで、
`followKeyboard()` も「ピンチで拡大している間（`scale > 1.01`）は
ずらす量を 0 に戻す」と、拡大されている状態を前提に書いてある
（TODO-039）。止めるほうが退行になる。

### 受け付ける条件の値を実機に合わせる

reviewer から、確信度が低い指摘として 2 件出た。**どちらも今は変えない。**

- **`SWIPE_MAX_MSEC = 800` は取りこぼす方向に効く。** 誤検出よりは
  取りこぼしに倒してある。意図した配分でよいかは実機で使ってみないと
  分からない
- **`SWIPE_EDGE_PX = 30` より画面端スワイプの受付幅が広い端末が
  あるかもしれない。** この幅は端末と OS の版で変わる

どちらも手元の環境では確かめようが無く、直したかどうかを確かめられない。
実際に使って具合が悪ければ、そのとき値を見直す。
