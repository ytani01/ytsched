# TODO-020 の分担

## 誰に何を担当させたか

| 担当 | 何をしたか | 報告 |
| --- | --- | --- |
| main | 着手時の調査、サブエージェント定義の書き直し、実装方針の決定、依頼書の作成 | — |
| implementer | 読み書きの JSON Lines 化、正規化、移行ツール、テスト | implementer-report.md（依頼は [implementer-request.md](implementer-request.md)） |
| verifier | テスト・lint・起動確認、移行ツールを実データ相当で動かす | verifier-report.md |
| reviewer | 分岐と条件式の意味が変わった箇所を見る | reviewer-report.md |
| writer | `CLAUDE.md` の「データモデルの勘所」と `docs/data-format.md` の状態の記述 | writer-report.md |

## なぜこの分担にしたか

項目を立てたときの見込みは `implementer + verifier + reviewer`。
着手時に **writer を足した**。`CLAUDE.md` の「データモデルの勘所」は
旧形式の説明そのままで、書き直す量が節ひとつ分ある。`~/.claude/CLAUDE.md`
の「文書の下書きには Sonnet 以下を充てる」に当たり、実装の担当に
続けてやらせるより分けたほうがよいと判断した。実装が済んでから
実物を読ませて書かせる。

reviewer を入れたのは TODO-017 の基準（挙動や分岐が変わる項目には入れる）
そのままで、この項目では次の 2 つが変わる。

- **判定の正規化** — 「重要」「取り消し」の判定条件が、全角括弧でも
  効くようになる。`（重要）打合せ` が入力直後と再読み込み後で食い違って
  いたのが揃う。条件式の意味が変わるので、テストが通ることを見ても
  捕まえられない
- **壊れた行の切り分け** — 「ファイル全体を捨てる」から「その行だけ
  飛ばす」へ変わる。どの行を飛ばすかの条件が新しく増える

## 着手時に分かったこと（定義ファイルとの食い違い）

`.claude/agents/*.md` の 4 つすべてに、

> **データ形式（タブ区切りテキスト）とデータディレクトリ `~/ytsched/data` は
> 変えない。** 既存データとの互換のため

と書いてあった。TODO-018 でデータ形式を JSON Lines へ移すと決めたので、
この項目とまっすぐ食い違う。そのまま implementer を起動すると、依頼と
定義のどちらに従うかを担当に判断させることになる。

利用者に確認したうえで、4 つとも次の形に書き直した。

- データディレクトリ `~/ytsched/data` の**場所**は変えない
- データ形式は JSON Lines へ移行中（TODO-020）で、仕様は
  `docs/data-format.md` にある
- `Conf.cgi` の形式を変えない（TODO-011）のはそのまま

reviewer の「見るもの」にあった「データ形式を変えていないか」も、
「データ形式が `docs/data-format.md` の仕様どおりか」に直した。

**Claude Code は起動時にしか定義を読まない**ので、書き直したあとに
利用者が再起動してから担当へ依頼した。

`~/.claude/CLAUDE.md` の「作業の内容が常設の定義に合わなくなってきたら、
定義し直す。見直すのは項目を立てるとき」に照らすと、**本来は TODO-020 を
立てた時点（TODO-018 で形式を変えると決めたあと）で気づくべきだった。**
担当を割り当てる際に既存の定義で足りるかを見る、という手順を踏んで
いれば出てきた。

## main が決めたこと

依頼書に書いた実装方針のうち、`docs/data-format.md` に書いていなくて
main が決めたもの。

- **移行ツールは CLI のサブコマンド**（`ytsched migrate`）。TODO-020 で
  「実装時に決める」となっていた点。`uv tool install` したコマンドから
  そのまま使えるほうがよいため（利用者に確認済み）
- **読み込みはバイナリで読んで `split(b"\n")` で切る。**`splitlines()` は
  U+2028 でも切るので、`detail` に U+2028 が入った 1 件が 2 行に割れる。
  仕様書は移行ツールについてこれを書いているが、読み込み側にも同じことが
  当てはまる
- **正規化を使う場所は 3 か所に限る。**`is_todo()` と `is_holiday()`
  （`type` を見る判定）は変えない。仕様書が正規化の対象に挙げていない
- **`main_handler.py` の検索文字列の `.lower()` はそのまま。** 仕様書の
  「検索文字列そのものは正規化しない」に当たる
- **`mk_dataline()` という名前は残す。** 「ファイルに書く 1 行」を返す
  役目は変わらないため
