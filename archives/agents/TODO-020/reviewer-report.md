### 1.［中］移行時、euc_jp の行が utf-8 として読めてしまうと、警告なしに文字化けする

`src/ytsched/migrate.py:63-70`（`decode_line()`）

utf-8 → euc_jp の順に**行ごとに**試すため、euc_jp のバイト列がたまたま
utf-8 として妥当な行は、utf-8 として読まれて別の文字になる。
`UnicodeDecodeError` が出ないので**警告も出ず、error-file にも残らない**。

実測（この環境で確認）:

```python
"丹".encode("euc_jp")            # b'\xc3\xb0'
b'\xc3\xb0'.decode("utf-8")      # 'ð'  ← 例外にならない
```

単独でこうなる文字は U+3000〜U+9FFF の範囲に **930 文字**ある
（`与` `丹` `乃` `之` `乏` など）。行の**全バイト**が utf-8 として妥当で
ないと起きないので、日本語が数文字以上ある行では実質起きない。
危ないのは「非 ASCII が 1〜2 文字しか無い短い行」（`title` が 1 文字、
`type` だけ、など）。よく使いそうな短い語 40 個を試した範囲では
該当は無く、**発生確率は低い**。

問題は確率ではなく、**起きても気づけない**こと。旧コードはファイル単位で
デコードしていたので（ファイル全体が utf-8 として妥当になる必要があり）
この経路は事実上無かった。移行は一度きりで、変換後は `.jsonl` のほうを
使い続けるため、あとから見つけにくい。

**`docs/data-format.md` の手順 1 が「行ごとにデコードする」と決めている**
ので、直すなら仕様のほうも書き直しが要る。判断は main。
（安く済ませるなら、ファイル全体が utf-8 としてデコードできるかを先に 1 回
見て、できないファイルは行ごとに euc_jp を先に試す、あるいは「同じ
ファイル内で utf-8 の行と euc_jp の行が混在した」ことを報告する、など。）

`src/ytsched/webapp.py:82` / `src/ytsched/ytsched.py:656`（`DEF_CACHE_SIZE = 20000`）

`src/ytsched/ytsched.py`（`load()` の `skipped_lines.append(raw_line)`）

## 確かめたこと（依頼の重点 1〜6）

### 1. 書き戻しの実装 — 増える／消える経路は見つからなかった

一時ディレクトリで実際に動かして確かめた（実データには触れていない）。

- 良い行 1 + 壊れた行 1 + 空行 1 のファイルに対し、
  **`SchedDataFile` を作り直して（＝ `load()` を挟んで）add → save を
  3 回**くり返した。行数は 2 → 3 → 4 → 5 と、足した分しか増えず、
  壊れた行と空行は 1 つずつのまま。`skipped_lines` も
  `[b'{ broken', b'']` のまま増えなかった
- **同じオブジェクトで `save()` を 3 回連続**しても、ファイルは変わらない
- **全行が壊れているファイル**（`[1,2]` と `{ x` の 2 行）では `sde` が 0 件、
  `skipped_lines` が 2 行。保存を 2 回くり返しても、**本体と `.bak` の
  両方に 2 行とも元のバイトのまま残った**。
  `docs/data-format.md` が旧形式の消失例として挙げている経路が、
  実際に閉じていることを確認できた

増殖しない理由は、`load()` の先頭で `skipped_lines` を空に戻すことと、
`save()` がファイルを丸ごと書き直すこと。`SchedData` 経由
（`add_sde()` / `del_sde()` → `save()`）でも、キャッシュから返るのは
同じ `SchedDataFile` オブジェクトなので、二重に持つことはない。

### 2. バイナリ書き出し — 通常のデータが壊れる経路は増えていない

- `mk_dataline()` は `json.dumps()` の結果で、改行・タブ・U+2028 を
  含んでも 1 行になる（`test_mk_dataline_is_one_line` が押さえている）。
  よって `line.encode("utf-8") + b"\n"` は、従来のテキストモードの
  書き出しと同じバイト列になる。POSIX ではテキストモードも改行を
  変換しないので、既存ファイルの見え方は変わらない
- 最終行の改行は 1 つのまま。`test_no_broken_line_writes_nothing_extra` が
  **ファイル全体のバイト一致**で押さえているので、余分な改行が入れば落ちる
- `.bak` の仕組みは無変更（存在 かつ サイズ > 0 なら `shutil.move`）。
  書き戻しのぶん本体が空になりにくくなったが、「空のファイルは退避
  しない」という規則自体は動いていない

### 3. `skipped_lines` の初期化のタイミング — 問題なし

`load()` の**先頭**（`FileNotFoundError` を捕まえる `try` より前）で
`self.skipped_lines = []` に戻している。したがって読み直しで前回分が
残らず、ファイルが消えていた場合も空に戻る（消えたファイルへ書き戻す
ことはない）。`__init__()` 側の初期化は `self.sde = self.load()` より前に
あり、`load()` の中の代入と重複するが害は無い（`load()` を外から
呼んでも安全になる）。

### 4. `split_lines()` の共通化 — 移行ツールの挙動は変わっていない

`SchedDataFile.split_lines()` は staticmethod で、中身は削除された
`migrate.split_lines()` と同一（末尾の改行を 1 つ落として `b"\n"` で切る）。
`tests/data/old_format/` を一時ディレクトリへコピーして
`ytsched migrate` を実行し、**共通化する前の変換結果と全 8 ファイルが
バイト単位で一致**することを確認した（8 ファイル・27 行・飛ばした行 0）。

`implementer-report.md` の「空行の書き戻しをやめた（2026-08-21）」の差分
だけを見た。「直さなくてよい」と決まったもの（`dict_time()` の
`TypeError`、移行ツールの終了コード）には触れていない。

**不具合は見つからなかった。** 依頼の重点 1〜5 は、下の「確かめたこと」の
とおりいずれも問題なし。指摘は 1 件だけで、重要度は低い。

## 指摘

### C.［低］移行ツール側だけ、空行の判定が直書きのまま

`src/ytsched/migrate.py:273`

```python
if not raw_line.strip():
    self.stat.empty_lines += 1
```

`SchedDataFile.is_empty_line()` にまとめたのに、`Migrator.conv_file()` は
同じ判定を直書きで持っている。いまは中身が同一なので**挙動は同じ**。
`conv_file()` は既に `SchedDataFile.split_lines()` を呼んでいるので、
`SchedDataFile.is_empty_line()` も同じように呼べる。

ずれても壊れ方は軽い（移行ツールは書き戻しをしないので、影響は
`stat.empty_lines` の数え方が変わる程度）。「空行とは何か」を 1 か所に
まとめた直後なので、揃えるなら今、という程度の話。判断は main。

## 確かめたこと（依頼の重点 1〜5）

一時ディレクトリで実際に動かして確かめた（実データには触れていない）。

### 1. 空行の判定は 1 か所にまとまっている（アプリ側）

`SchedDataFile.is_empty_line()`（staticmethod、`not raw_line.strip()`）を、

- `load_line()` — 「飛ばす」側（警告を出して `None` を返す）
- `load()` — 「書き戻さない」側（`skipped_lines` に積むかどうか）

の**両方が呼んでいる**ので、片方だけ空行扱いになる食い違いは起きない。
`load()` は `load_line()` が `None` を返したあとに `is_empty_line()` を
もう一度見る形だが、述語が同じなのでずれようがない。この順序は、将来
`load_line()` が別の理由で `None` を返すようになっても**書き戻す側
（安全側）に倒れる**ので、向きとしても良い。

上の指摘 C のとおり、移行ツールだけが直書きのまま。

### 2. 末尾の改行の扱いは変わっていない。縮み続ける経路も無い

「良い行 2 + 途中の空行 + 空白だけの行 + `{ x` + euc_jp のバイト列 +
末尾の余分な改行」というファイルで、`load()`→`save()` を 3 回くり返した。

- 1 回目で空行 3 つが落ち、以降は **287 バイトでバイト単位に不変**
  （2 回目・3 回目でファイルが変化しない）
- 末尾の改行は 1 つのまま。行数 4（良い行 2 + 壊れた行 2）
- `skipped_lines` は `[b'{ x', b'\xb2\xf1\xb5\xc4']` のままで増減なし

`split_lines()` が落とす末尾の改行 1 つと、空行の判定が二重に効いて
縮んでいく経路は無い。理由は、`save()` が各行に `\n` を 1 つだけ付けて
書くので、**保存後のファイルは必ず「改行 1 つで終わる」形に落ち着く**
（`split_lines()` はその 1 つを落とすだけで、空行を作らない）。

境界も確かめた。

- **末尾に改行が無いファイル** — 1 回目の保存で改行が 1 つ付き、以降は不変
  （行が消えたり増えたりしない）
- **空行だけのファイル**（`b"\n\n\n"`） — 本体は空になり、`.bak` に元の
  バイトが残る。2 回目の保存では本体が空なので `.bak` は上書きされない
  （「空のファイルは退避しない」規則がそのまま効いている）。失うデータは
  もともと無い

### 3. 残る 4 種類の書き戻しは、これまでどおり効いている

上の実測で、`{ x`（JSON として読めない）と euc_jp のバイト列（utf-8 で
デコードできない）が**元のバイトのまま**書き戻されることを確認した。
テストも 4 種類（デコード不可・JSON 不可・オブジェクトでない・`date`
無し）を parametrize で押さえている。

**絞りすぎていないこと**も確かめた。`bytes.strip()` が落とすのは ASCII の
空白（`空白 \t \n \r \v \f`）だけなので、`is_empty_line()` が真になる行に
データは残らない。

- 全角空白だけの行（euc_jp の `b"\xa1\xa1"`）→ 空行**ではない**と判定され、
  書き戻される
- `b"\x00"` だけの行 → 同上（`strip()` では落ちない）

### 4. 「全行が壊れているファイル」のテストは意味のある条件を見ている

`test_all_lines_broken_survives_two_saves` は、

- 読み込み直後に `sde == []` かつ `skipped_lines == [b"[1, 2]", b"{ x"]`
  （＝ 0 件として扱われる旧形式の状況を作れている）
- 追加 → 保存を 2 回くり返したあと、**本体と `.bak` の両方**が元の 2 行を
  バイト列のまま末尾に持つこと
- 本体が 4 行で、二重に書かれていないこと

を見ている。`.bak` 側は、2 回目の保存で「1 回目の本体」に置き換わるので、
`endswith(raw)` が通ることが**書き戻しが効いている証拠**になっている
（書き戻しが無ければ `.bak` から壊れた行が消え、落ちる）。
`docs/data-format.md` が旧形式の消失例として挙げている経路の固定として
過不足ない。

**空行側のテスト**（`test_empty_line_is_not_written_back` /
`test_empty_line_warning_stops_after_save`）も、ファイル全体のバイト一致と
「2 回目の読み込みで警告が出ない」を見ており、意味のある条件になっている。

軽い抜けとしては、空行のテストが 2 つとも**ファイル末尾に足す**形だけで、
**行の途中の空行**を落とすケースが無い。ただし `load()` に位置による
分岐は無く、既存の `test_load_broken_line_is_skipped` が途中の空行を
（飛ばす側で）押さえているので、実害は薄い。

### 5. 例外の握り潰し・黙って失敗する経路

新しい `try` / `except` は増えていない。`is_empty_line()` は
`not raw_line.strip()` を返すだけで例外を出さない。空行を落とすときも
`load_line()` が `empty line .. ignored` の警告を出しており、黙って消える
わけではない（保存後は消えるので、警告も止まる＝意図どおり）。
