## 確度の高い指摘

### 1. `delete()`/`clear()` のあと `trash.jsonl` のパーミッションが 0644 → 0600 に変わる

`_write_lines()` は `tempfile.mkstemp()` で作った一時ファイル（既定の
モードは所有者のみ読み書き可の 0600）へ書いてから `Path.replace()` で
差し替えている。実際に確認した。

```
before: 0o100644
after clear: 0o100600
```

一度でも `delete`/`clear` を呼ぶと、それ以降 `trash.jsonl` は 0600 の
ままになる（`add()` は既存ファイルを `"ab"` で開くだけなので、
パーミッションはそこで変わらない）。既存の `SchedDataFile.save()`
（`ytsched.py`）は `pathname.open(mode="wb")` で直接上書きしており、
既存ファイルのパーミッションを保つ。今回の書き方はその慣習と違う。

単一ユーザ用アプリで、依頼書にも「バックアップの運用」までは書かれて
いないので実害があるかは分からないが、依頼書で明示的に確認を求められた
点（「パーミッション」）なので報告する。直すなら、`_write_lines()` の
中で `os.chmod`（または `os.fchmod`）を使い、元の `trash.jsonl` の
パーミッションを一時ファイルへ引き継ぐとよい。**直すかどうかは
main の判断。**

## 気になるが確度は低いもの

### 2. `TrashFile.delete()` は一致する行を「全て」取り除く

同じ `sde_id`/`trashed_at`（マイクロ秒まで持つ）の組が複数行あることは
実質無い想定で、docstring にもそう書いてある。1 件消すボタンから
呼ばれる分には実害は無いはずだが、「一致条件」を明示的に見てほしいと
依頼にあったので触れておく。実装判断としては妥当で、直すべきとは思わない。

### 3. 1 件削除後のリダイレクト先は常に絞り込み無しの `/trash`

`?sde_id=` で絞り込んで開いている状態で 1 件削除すると、
`_delete()` は常に `{url_prefix}trash`（絞り込み無し）へリダイレクトする。
削除後に絞り込みが外れる。依頼書は「空にする」を出す条件にしか
`sde_id` に触れていないので範囲外の可能性が高いが、体験としては
気になったので書いておく。

### 4. `_write_lines()` と `add()` の競合について（確認した結果、問題は見当たらなかった）

依頼で名指しされていた点なので確認した。`TrashHandler`/`MainHandler`/
`EditHandler` はいずれも同期メソッド（`async def` ではない）で、
`webapp.py` は `HTTPServer.listen()` を単一プロセス・単一スレッドの
`IOLoop` で回しているだけ（`fork_processes` などは無い）。そのため
1 リクエストの処理中は他のリクエストが割り込まないはずで、
「`delete()`/`clear()` の読み込みと書き直しの間に別リクエストの
`add()` が挟まって、追記した行が消える」という懸念は、今の構成では
起きないはず。将来マルチプロセス化するときは注意が要る、という
メモとして残す。
