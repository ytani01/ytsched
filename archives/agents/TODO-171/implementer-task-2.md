# TODO-171 implementer への依頼（2 回目）

reviewer が復活の版の決め方に穴を見つけた。塞ぐ。
`archives/agents/TODO-171/reviewer-report.md` の「1.」に再現手順がある。
**先にそれを読むこと。**

## 何が起きるか

日付を変える編集をすると、生きている予定は**別の日付のファイル**へ移る。
`_restore_id()` は「ゴミ箱」と「復活させる行自身の日付のファイル」しか
見ていないので、移った先の予定に気づかず、復活した予定が生きている予定と
同じ `sde_id` になる。

生きている予定の版が「ゴミ箱の最大 + 1」になるという見立ては、
日付を変える編集でも、復活を 2 回続けても崩れる。部分的に見て回る
やり方では塞がらない。

## 直し方

**復活のときだけ、データディレクトリ全体を走査する。** 同じ UUID を持つ
`sde_id` の最大の版を探して + 1 にする。復活は滅多に使わない操作なので、
全走査の費用を払ってよい。

- `SchedData` に、UUID を渡すと最大の版を返すメソッドを足す
  （同じ UUID が無ければ `0`）。走査するのは
  `{年}/{月}/{日}.jsonl`・`ToDo.jsonl`・`trash.jsonl` の 3 つ。
  `.bak`・`.cgi` は対象外
- ゴミ箱の分は、いまある `TrashFile.max_version()` をそのまま使う
  （消さない）。`SchedData` 側は予定のファイルを走査して、
  その結果と合わせて最大を返す
- **走査するファイルの列挙を 2 か所に書かない。** いま
  `IdFixer.find_files()` が同じ列挙を持っているので、列挙は 1 か所に
  まとめて両方から使う。置き場所は `ytsched.py` 側（データの並びを
  知っているのはこちら）にして、`IdFixer` がそれを使う形にする
- 走査は 1 行ずつ読み、**UUID の文字列が含まれない行は JSON として
  解析せずに飛ばす**（13000 行あるので、全行を解析しない）。
  読めない行は飛ばす（`SchedDataFile.load()` と同じ考え方）
- `trash_handler._restore_id()` は、この 1 つのメソッドの結果 + 1 を
  使う形に整理する。いまの「復活先の日付のファイルを見る」処理は、
  全走査に含まれるので消してよい
- 元の ID が新しい形式でないときは、いまどおり新しい ID を発行する

## テスト

- 新しいメソッド単体 — 日々のファイル・`ToDo.jsonl`・`trash.jsonl` の
  それぞれに散らばった同じ UUID から最大の版を拾うこと。
  同じ UUID が無ければ `0`。**別の UUID の版を拾わないこと**
- **reviewer の再現手順をそのままテストにする。**
  予定を作る → 日付を変えて編集する → 古い版を復活させる →
  復活した予定の `sde_id` が、生きている予定とも、ゴミ箱の行とも
  重ならないこと
- いまある復活のテストは残す

## 文書

`docs/data-format.md` のゴミ箱の節（復活の説明）を、新しい決め方に
合わせて直す。「ゴミ箱と復活先の日付のファイルの両方」と書いてある
ところが、いまの実装と合わなくなる。
