# TODO-171 の分担

`sde_id` の末尾にバージョン番号を付ける件（`TODO.md` の TODO-171）。

## 分担

| 担当 | やったこと | 依頼 | 報告 |
|------|-----------|------|------|
| main | 仕様を決める。reviewer の指摘の扱いを判断する | — | — |
| implementer | 実装・テスト・文書 | [1 回目](implementer-task.md) / [2 回目](implementer-task-2.md) | [報告](implementer-report.md) |
| verifier | テスト実行、`fix-id` の実行、画面での確認 | [依頼](verifier-task.md) | [報告](verifier-report.md) |
| reviewer | 正しさ・設計のレビュー | [依頼](reviewer-task.md) | [報告](reviewer-report.md) |

## この分担にした理由

- **implementer を分けた** — 複数のファイル（`ytsched.py`・
  `sched_update.py`・`trash.py`・`trash_handler.py`・`fix_id.py`・
  テンプレート）に、テストと文書がまとまって要る規模だったため
- **reviewer を入れた** — 挙動が変わるうえに、`fix-id` が全データを
  一括で書き換える。失敗すると実データが壊れる
- **verifier を入れた** — `fix-id` は実際に走らせないと分からない
  （対象のファイル、キーの並び、更新時刻）。画面の一連の操作も試せる

## 結果

- **reviewer の指摘が効いた。** 「日付を変える編集のあとに古い版を
  復活させると、別の日付のファイルにいる生きた予定と同じ ID ができる」
  という経路を、再現手順つきで出した。テストが通ることを見ても
  出てこない種類の指摘で、実装した本人（implementer）も、
  画面を触った verifier も気づいていなかった
- 塞ぎ方（復活のときだけデータディレクトリ全体を走査する）は main が
  決め、2 回目の依頼として implementer に出した。指摘した本人には
  直させていない
- **verifier の発見はゼロ**だったが、`fix-id` を 4 通りのデータで
  実際に走らせ、画面で作成 → 編集 → 復活 → 削除まで通した。
  直しのあとにも同じ確認をやり直させ、reviewer の再現手順が実際に
  塞がったことを画面で見せた

## 途中の仕様変更

版のゼロ埋め（`-001`）をやめて `-1` にした。999 を超えたら桁が伸びる
以上、3 桁に揃えても揃わないので、ゼロ埋めする意味がないため。
implementer の作業中に伝えた。

複製（TODO-127）でも版を増やして「修正 = 複製 + 削除」に揃える案も
出たが、**採らなかった**。複製した直後は元と複製が両方生きているので、
そのあと元を修正すると複製と同じ版になって ID が衝突する。避けるには
修正のたびに全走査が要る。ゴミ箱のグループの意味も「同じ予定の編集
履歴」から「複製の系統」に変わってしまう。
