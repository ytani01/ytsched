## 特に見てほしいところ

1. **`fix-id` は全データを一括で書き換える。** 失敗すると実データが
   壊れる。書き戻しの手順（一時ファイル → `replace`）、例外のときに
   元のファイルが残ること、`trash.jsonl` を対象に加えたことで新しく
   壊れる余地が無いかを見る

2. **ID の分解・生成**（`SchedDataEnt.split_id()`/`id_uuid()`/
   `id_version()`/`format_id()`/`next_id()`）。版の付いていない UUID や
   旧形式の ID、ゼロ埋め、想定外の文字列を渡したときに、
   誤って分解したり、中途半端な形の ID を作ったりしないか

3. **ID が重複しないか。** 編集・複製・復活・削除のそれぞれで、
   生きている予定どうし、あるいは生きている予定とゴミ箱の行で、
   同じ ID ができる経路が無いか。特に**復活**の版の決め方
   （ゴミ箱と復活先の日付ファイルの両方の最大版 + 1）に穴が無いか

4. **ゴミ箱の絞り込みの緩和**（完全一致 → UUID 部分の一致）で、
   `get()`・`delete_many()`・復活・完全削除が、狙っていない行に
   当たるようになっていないか

5. テストが、仕様の要点を実際に押さえているか（通ることではなく、
   何を見ているか）

6. プロジェクトの決まり（`CLAUDE.md`・`src/README.md`・
   `docs/data-format.md`）からの逸脱。ログは `mylog.py` のラッパか、
   文書の書き換えが実装と合っているか
