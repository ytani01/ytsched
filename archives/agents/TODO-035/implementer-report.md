## 単独で決めた判断

1. **始点・終点の検索は、コミットメッセージの 1 行目だけを見る。**
   依頼書は「本文に `TODO-NNN` を含むもの」だったが、そのとおりに実装したら
   **TODO-029 の始点が 4b68048（TODO-034 を立てたコミット）になった**。
   4b68048 の本文に「TODO-029 の reviewer と…」とあるため。
   1 行目だけを見れば `docs(todo): … を TODO-029 として立てる` /
   `fix(...): …（TODO-029）` という決まりに一致し、実際に正しい
   ecbd3b5 を拾えた。`CLAUDE.md` のコミット規約でも番号は 1 行目に入る。
2. **始点より古い終点は使わない。** 同じ番号で立て直した項目（TODO-022 /
   TODO-013）があり、終点が始点より古くなる。その場合は警告を出して
   「まだ完了していない」扱いにした。
3. **引数の解釈は `argparse`。** 依頼書の「標準ライブラリだけで書く」に
   従った。プロジェクト本体は click だが、`tools/` はパッケージ外なので
   揃えなかった。
4. **ログは `mylog.py` を使えた。** `uv run` なら `ytsched` が editable で
   入っているので `from ytsched.mylog import ...` が通る。`print` への
   退避は不要だった。`-d` / `--debug` を付けたときだけ内部の数を出す。
5. **transcript のディレクトリはカレントディレクトリから導く**（依頼書
   どおり）。見つからないときは「プロジェクトのトップで実行してください」と
   出して終了コード 1。集計より先にこの確認をするので、何も出さずに落ちる。
6. **重複除去は全ファイルにまたがって行う。** 実測では親と subagents の
   間に重複は無かったが、セッションを再開すると同じメッセージが複数の
   `.jsonl` に入りうるので、`(requestId, message.id)` の集合は全体で 1 つに
   した。範囲で絞ってから除去している。
7. **表の桁揃えは表示幅で計算**（`unicodedata.east_asian_width`）。
   「担当」「合計」などの全角がずれるため。
8. **`<synthetic>` モデルの行も落とさずに数える**（実測 4 件、すべて 0
   トークン）。除外の判断を入れるより、見えているほうがよいと考えた。

## 「3. 書く形」についての見立て

実際の出力（TODO-034）:

```
消費: output 21,282 / cache_creation 163,913（main 64% + verifier 18% + wording 18%）
（参考: cache_read 4,671,282、メッセージ 90 件）
```

- **依頼書の案（1 行目）はそのままで読みやすい。** 桁は output が 5 桁、
  cache_creation が 6 桁で、`,` 区切りがあれば十分読める。
- **担当の割合は残す価値がある。** TODO-034 は main 64%、TODO-029 は
  main 37% + implementer 26% と、項目によってはっきり違いが出た。
  「どの担当で足りたか」を振り返る材料になる。割合は
  `output + cache_creation` で計算している。
- **2 行目（参考）は archives に貼らなくてよいと思う。** cache_read は
  4.6M と桁が 1 つ違い、貼ると 1 行目が霞む。ツールの画面では出すが、
  TODO ファイルには 1 行目だけ貼る、を勧める。**決めるのは管理者。**
