# Obsidian 向け Markdown 案へのコメント

対象は [obsidian-format-review.md](obsidian-format-review.md) である。
ここでは文書の書き方ではなく、結論と検討の前提についてコメントする。

## 総評

完全移行案 A を、そのまま「1 件 1 ファイルの Markdown」に置き換える
案としては、慎重であるべきという結論に賛成する。現行は日ごとの
キャッシュをまとめて保存するため、Obsidian とアプリが同じデータを
編集するなら、変更の検出と競合の扱いを先に決めなければデータを失う。

ただし、「アプリの挙動は一切変えられない」や「避けようが無い 3 点」
は、この時点では結論として強すぎる。ファイル形式を変えることと、画面や
検索結果など利用者に見える挙動を変えることは分けて考えるべきである。
実装を増やせば維持できるものと、Obsidian での表示・編集を受け入れる
以上は変わるものを、区別して判断したい。

## 賛成する点

- **同時編集を最重要の論点にしたこと**

  `SchedDataFile.is_stale()` は 1 ファイルの `mtime` とサイズだけを比較し、
  保存時にはその日を全件書き直す。日をディレクトリにして各ノートを
  Obsidian から直せるようにするなら、現状のままでは変更を見落とし、
  アプリの保存で編集を失う。これは形式の見た目より先に解かなければならない。

- **データに基づいてファイル名案を退けたこと**

  表題の空、使えない文字、同名、既存 `sde_id` の重複を数えているため、
  `{時刻}-{表題}.md` や `{sde_id}.md` を安易に採れないことが分かる。
  人が読めるファイル名だけで一意性と不変性を両立させるのは難しい。

- **一方向の書き出しを候補に残したこと**

  Obsidian で読む、検索する、他のノートから参照することが目的なら、
  元データを変えずに試せる。大きな移行を決める前に、Obsidian が実際に
  役に立つかを確かめる方法として価値がある。

## 再検討したい点

### 「避けようが無い」3 点

5-1 の問題は、現行の `is_stale()` のままでは避けられない。しかし、
日ごとの全ノートを `stat()` して状態を記録する、ファイル監視でキャッシュを
無効にする、保存前に変更を検出して競合として止める、といった方法はある。
どれも実装量、速度、対応 OS の条件を増やすが、不可能ではない。

5-2 の同時刻の順序も、移行時の順番を不変の `sort_order` として保存すれば
保てる。Obsidian で新規作成・並べ替えをどう受け付けるかは別途必要だが、
「ファイル名を順番に使う」だけが方法ではない。

5-3 は、保存する値と Obsidian の表示を分けるべきである。Markdown の本文を
生の文字列として読めば、`#` や `---` を含む値自体は保持できる。一方で
Obsidian では Markdown として表示されるため、同じ文字列がアプリと異なって
見える。この表示上の差と、前後空白などが編集時に変わる危険は重要だが、
「保存する文字列を保てない」とは別の問題である。

したがって、完全移行案を見送る根拠は「不可能」ではなく、**双方向編集を
安全にするための設計と実装が大きい**とするのが適切である。

### 案 B を勧める前提

案 B は安全だが、Obsidian で編集したいことが主目的なら目的を満たさない。
「Obsidian で読めるようにしたい」のか、「Obsidian を予定の編集画面として
使いたい」のかを、先に利用者へ確認する必要がある。後者なら、書き出しだけを
作っても本格的な設計判断を先送りするだけになる。

また、書き出しだけでも次を決めなければ使い勝手を評価できない。

- 書き出し先は vault 内の専用ディレクトリにし、生成物を手で直さないと
  明示するか。
- 同じ予定には、再書き出し後も変わらないファイル名を与えるか。
- 予定の更新・削除時に、対応する Markdown を更新・削除するか。
- 書き出しは手動コマンド、アプリ保存時、自動実行のどれにするか。

限定すれば、5-1 の競合を検出して止められる。

## 完全移行案へ進む場合の条件

完全移行を選ぶなら、形式を決める前に次を決めたい。

1. 正本はアプリと Obsidian のどちらに置くか。両方を正本にするなら、競合時に
   どちらを残すか。
2. ノートを識別する不変のキーをどう持つか。既存の `sde_id` は重複があるため、
   ファイル名とは別に移行用の一意なキーを追加する案が必要になる。
3. 同時刻の予定の順序を、移行前と移行後でどう保つか。
4. Obsidian で新しいノート、削除、改名をしたとき、それぞれを予定の追加・削除・
   更新として扱うのか。
5. アプリ保存前に外部変更を見つけたとき、上書きせずエラーにするのか、比較画面を
   出すのか、Obsidian 側を優先するのか。

これらに答えが出ない間は、データ形式の移行ではなく、生成専用の書き出しを
試す段階にとどめるのが妥当である。
