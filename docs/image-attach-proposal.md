# 予定への画像添付（提案）

**状態: 未実装の提案。** 各予定（`SchedDataEnt`）に画像を複数枚
添付し、一覧と編集画面で見られるようにするための検討結果である
（TODO-169）。実装するかどうか、どの案を採るかはこれから決める。

現行の仕様は [data-format.md](data-format.md)、
[../src/README.md](../src/README.md)、[Install.md](Install.md) にある。
この文書は現行仕様ではない。

## 1. 結論（推し）

| 決めること | 推す案 |
| --- | --- |
| 画像ファイルの置き場所 | `{datadir}/images/{年}/{月}/{ファイルID}.{拡張子}` |
| ファイル名 | UUID。**予定の `sde_id` も日付も使わない** |
| JSON Lines への持たせ方 | `"images"` キーに相対パスの配列を足す |
| アップロードの経路 | 編集画面の既存フォームを multipart にする |
| 縮小 | ブラウザ側で送信前に縮小（サーバに依存を足さない） |
| 配信 | `/ytsched/img/` に `StaticFileHandler` を 1 つ足す |
| 予定を消したときの画像 | **消さない。** 別コマンドでまとめて掃除する |
| 一覧での見せ方 | 詳細の折りたたみと同じ開閉スイッチの中にサムネイル |

いちばん効くのは 2 行目である。理由は次章に書く。

## 2. 前提: 予定の identity は当てにできない

このアプリの更新は、内部では **削除してから追加** になっている
（`SchedUpdater.exec_update()`）。そのため予定と画像を結び付ける鍵を
選ぶときに、次の性質を踏まえる必要がある。

| 操作 | `sde_id` | 保存先のファイル | 予定の JSON 行 |
| --- | --- | --- | --- |
| 修正（`fix` / `update`） | そのまま | 日付を変えれば別の日のファイルへ移る | 書き直される |
| 複製（`add`） | **新しく振り直す** | 同上 | 増える |
| 削除（`del`） | そのまま | 日ファイルから消え、`trash.jsonl` へ追記 | ゴミ箱に残る |
| 復活 | **新しく振り直す** | 表示中の日へ | ゴミ箱の行から作り直す |

さらに、旧形式から移ってきた `sde_id` は UUID ではなく、**実データでは
8 種類が重複している**（[data-format.md](data-format.md)）。

- **`{sde_id}/` のディレクトリに画像を置く案は採らない。** 重複した
  `sde_id` で画像が混ざる。複製と復活で `sde_id` が変わるため、画像が
  付いてこない
- **日付のディレクトリに置く案も採らない。** 日付を変えるたびに
  ファイルを移す処理が要る

一方、**JSON の行そのものは、修正でも複製でも削除でも復活でも
引き継がれる**。だから画像への参照を行の中（`images` キー）に持たせ、
ファイル名は予定と無関係な UUID にすれば、上の 4 つの操作すべてで
何も特別なことをせずに画像が付いてくる。複製すれば同じ画像を指す行が
2 つになるだけで、ゴミ箱の行にも `images` がそのまま残る。

## 3. データ形式

`SchedDataEnt` に `images` を足し、`to_dict()` / `from_dict()` で
読み書きする。

```json
{"sde_id": "3f2a…", "date": "2026-09-03", "time_start": "10:00", "time_end": "11:00", "type": "予定", "title": "打合せ", "place": "3F", "detail": "議題", "images": ["2026/09/2f1c8b04….jpg", "2026/09/9ad3e577….png"]}
```

| キー | 型 | 内容 |
| --- | --- | --- |
| `images` | 文字列の配列 | `{datadir}/images/` からの相対パス。**追加した順**に並べる |

- **欠けていれば空の配列**として読む。既存の行はそのまま読める
  （形式の決まりどおりの拡張）
- 配列でない値、要素が文字列でない、`..` や先頭の `/` を含むパスは、
  警告を 1 行出してその要素だけ捨てる。行は捨てない
- 書くときは、画像が 1 枚も無くても `"images": []` を出す
  （「書くときは全部のキーを出す」）

置き場所は次のとおり。

```
~/ytsched/data/
  2026/09/03.jsonl
  images/
    2026/
      09/
        2f1c8b04….jpg
        9ad3e577….png
```

- `images/{年}/{月}/` は **画像を追加した年月**で、予定の日付とは
  関係無い。だから予定の日付を変えてもファイルは動かない
- 1 つのディレクトリにファイルが溜まりすぎないための区切りでもある

判断が要る点: **元のファイル名を残すか。** 残すなら値を文字列ではなく
`{"file": "...", "name": "IMG_0123.JPG"}` の形にする。あとから
「文字列も dict も読む」形に広げられるので、まずは文字列で始めて
よいと考えている。

## 4. アップロードの経路

### 案 A（推し）: 既存フォームを multipart にする

`edit.html` の `<form>` に `enctype="multipart/form-data"` と
`<input type="file" accept="image/jpeg,image/png,image/webp" multiple>`
を足すだけで、送信先も流れも今までと変わらない。

- 受け取りは `MainBinder`（`self.request.files`）で、
  `SchedUpdateForm` に「新しく足す画像」と「外す画像」を積んで
  `SchedUpdater` へ渡す。ファイルを書くのは `TrashFile` と同じ形の
  新しいクラス（`images.py` の `ImageStore`）にして、
  **`SchedUpdater` は tornado を知らないまま**にする
- POST-Redirect-GET のままなので、リロードで二重に送られることも無い
- ブラウザ側のスクリプトは、縮小（後述）を足すだけで済む

### 案 B: 専用のエンドポイントへ非同期で送る

`/ytsched/upload` を作り、`fetch()` で送って即座にサムネイルを出す。
進捗も出せる。ただし **今のコードには `fetch()` も `XMLHttpRequest` も
1 つも無い**。失敗したときの見せ方、保存せずに画面を離れたときに残る
孤児ファイルの掃除など、決めることが一気に増える。

案 A で困ってから案 B を考えるのでよい。

## 5. 縮小をどこでやるか

スマホの写真はそのままだと 1 枚 3〜10MB あり、週表示に何枚も出すと
読み込みが目に見えて遅くなる。

| 案 | 依存 | 原寸 | 備考 |
| --- | --- | --- | --- |
| 縮小しない | 増えない | 残る | 表示は CSS で縮むが、転送量はそのまま |
| **ブラウザ側で縮小（推し）** | 増えない | **残らない** | `canvas` で長辺を揃えてから送る |
| サーバ側で縮小 | **Pillow が増える** | 残る | 原寸と別にサムネイルを持てる |

推すのは 2 番目である。単一利用者・自分の写真だけという前提なら、
原寸を持ち続ける必要は薄く、依存を増やさずに済む。

- 長辺が閾値（1600px 程度）**以下ならそのまま送る**。超えたときだけ縮める
- **形式は変えない**（JPEG は JPEG、PNG は PNG、WebP は WebP）。
  画面写真を JPEG に寄せると文字がにじむ
- 向きは `createImageBitmap(blob, {imageOrientation: "from-image"})` で
  EXIF を反映させてから描く。これをしないと横倒しになる

判断が要る点: **原寸を残したいか。** 残したいなら Pillow を入れて
サーバ側で縮小し、原寸とサムネイルの 2 つを置く形になる。

## 6. 配信と受け入れの決まり

- **URL は `/ytsched/img/{相対パス}`。** `tornado.web.StaticFileHandler`
  に `path={datadir}/images` を渡して登録する。`..` を含むパスは
  `StaticFileHandler` 側が弾くので、その判定を自前で書かずに済む
- ファイル名は UUID で中身が変わらないため、キャッシュは長くしてよい
- **受け入れる形式は先頭バイトで判定する。** 拡張子だけを見ない。
  JPEG（`FF D8 FF`）、PNG（`89 50 4E 47`）、WebP（`RIFF` …… `WEBP`）の
  3 つで、判定は依存無しで 10 行ほどで書ける。保存する拡張子は判定結果に
  合わせて付け直す
- **上限を決める。** 1 枚あたりのバイト数（10MB 程度）と、1 予定あたりの
  枚数（20 枚程度）。定数で持つか `conf.json` で変えられるようにするかは
  判断が要る
- **リバースプロキシの上限に当たる。** nginx の `client_max_body_size` は
  既定 1MB で、そのままでは写真 1 枚で 413 になる。
  [Install.md](Install.md) に追記が要る。アプリ側の
  `WebServer.DEF_SIZE_LIMIT`（100MB）はすでにあるので足りている

## 7. 画像を消すとき

**予定を消しても、画像ファイルは消さない。** ゴミ箱から復活したときに
画像も戻るようにするためで、`.bak` を残すこと・ゴミ箱に残すこと・移行で
`.cgi` を消さないことと同じ考え方である。

編集画面で「外す」を選んだ画像も、行の `images` から消えるだけで
ファイルは残る（複製した別の予定がまだ指しているかもしれない）。

したがって、参照されなくなったファイルは溜まる。掃除は別に用意する。

```sh
ytsched gc-images --datadir ~/ytsched/data --dry-run
```

- すべての `.jsonl`（日ファイル・`ToDo.jsonl`・`trash.jsonl`）を読み、
  どの行からも参照されていないファイルを挙げる
- `--dry-run` を付けなければ消す。**既定では何もしない**
- `.bak` の中の行も参照とみなすかは判断が要る（みなすほうが安全だが、
  いつまでも消えない）

## 8. 画面

### 編集画面

日付・時刻・種別・表題・場所・詳細の下、ID の上に画像の欄を足す。

- 添付済みのサムネイルを横に並べ、各サムネイルに「外す」チェックボックス
- `<input type="file" multiple>` を 1 つ。スマホではカメラとギャラリーの
  どちらからでも選べる
- 送信は既存の保存ボタン（`fix` / `update`）と同じ

### 一覧（`sde.html`）

週表示は 1 画面に 1 週間を収める密度が要なので、**既定では開かない**。

- 詳細（`detail`）の折りたたみと同じ開閉スイッチの中に、サムネイルを
  横 1 列で置く（あふれたら横スクロール）
- 閉じているときは、アイコンと枚数だけを出して「付いていること」を示す
- サムネイルをタップすると全画面で見せる。**既存の折りたたみと同じ
  チェックボックスの仕組みを使えば、JS を足さずに書ける**

判断が要る点: **一覧に出すかどうか。** 編集画面でだけ見られれば足りる
なら、`sde.html` は「枚数の表示」だけで済み、変更はずっと小さくなる。

## 9. 実装の分け方

1 つの項目に収めると、データ形式・アップロード・表示・掃除の 4 つが
同時に動くことになる。3 つに分けるのを勧める。

| 項目 | 内容 |
| --- | --- |
| 1 | `images` キー、`ImageStore`、`/ytsched/img/`、編集画面での添付と表示 |
| 2 | 一覧（`sde.html`）でのサムネイルと全画面表示 |
| 3 | `ytsched gc-images` |

項目 1 だけでも「添付して、編集画面で見られる」ところまでは動く。

## 11. 選ばなかった案

- **画像を base64 にして JSON 行へ埋め込む。** ファイルが増えず、
  `.bak` とゴミ箱の仕組みにそのまま乗る。ただし 1 行が数 MB になり、
  `grep` やエディタで中身を見られるという今の形の利点が消える。
  保存のたびに全件を書き直す作りなので、`.bak` も含めて書き込み量が
  跳ね上がる
- **`detail` に `<img>` を手で書く。** `base.html` は
  `{% autoescape None %}` なので、実は今でも書けば表示される。ただし
  画像ファイルを置く手段が無く、置いても配信されない
- **外部のストレージやサービスに預ける。** 「外部サービスの影響を
  受けない」という前提（[../README.md](../README.md)）に反する

## 12. 決めること（まとめ）

1. 一覧にサムネイルを出すか、編集画面だけでよいか（8 章）
2. 原寸を残すか（残すなら Pillow を入れる。5 章）
3. 元のファイル名を残すか（3 章）
4. 上限の値と、`conf.json` で変えられるようにするか（6 章）
5. `ytsched gc-images` を作るか、当面は溜めっぱなしでよいか（7 章）
